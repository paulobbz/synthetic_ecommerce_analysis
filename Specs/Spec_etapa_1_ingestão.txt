CONTEXTO
Estou construindo um pipeline de dados em Python sobre um dataset sintético de comércio eletrônico. Trabalho com spec-driven development: a spec abaixo é a fonte da verdade e o código é consequência dela. Não acrescente requisito que não esteja escrito aqui. Se algo estiver ambíguo, pergunte antes de escrever código.

STACK
- Python 3.12 ou superior (a máquina tem 3.12.10; o pyproject.toml declara requires-python = ">=3.12"), dependências gerenciadas com uv
- pandas para ler os arquivos
- DuckDB, versão fixada em 1.5.6 (ver VERSÕES), banco no arquivo ecommerce.duckdb na raiz do projeto
- Nenhum orquestrador. Script executável pela linha de comando, no Prompt de Comando do Windows.

VERSÕES
V1. DUCKDB FIXADO
    No pyproject.toml a dependência é "duckdb==1.5.6", sem ">=" e sem teto.
    Motivo: na 2.0.0 a extensão ui falhou ao carregar no Windows (erro de
    inicialização de DLL); na 1.5.6 o ui.py funciona. Com ">=", o uv escolhe
    a versão mais recente do dia em que o projeto é criado, e o mesmo código
    passa a se comportar diferente conforme a data ou a máquina.
V2. uv.lock FAZ PARTE DO PROJETO
    O uv.lock fica na raiz, junto do pyproject.toml, e só muda por decisão
    explícita: nada de "uv lock --upgrade", e nada de "uv add duckdb" sem
    versão.
    Motivo: é o lock que faz "uv sync" reproduzir o ambiente que funciona.

O QUE JÁ EXISTE
A pasta raw/ com os sete .csv diretamente na raiz dela (clonados do repositório
paulobbz/synthetic_ecommerce_analysis), o pyproject.toml e o uv.lock. Nenhum
código ainda. Qualquer outra pasta de dados no projeto (como csv/) não faz
parte do pipeline: a única fonte é raw/.

ARTEFATOS A PRODUZIR, nesta ordem
1. pipeline/db.py, o módulo de conexão que as quatro etapas do curso vão importar (spec própria logo abaixo; é a primeira coisa a existir)
2. pipeline/ingestao.py, executável com:
     uv run python -m pipeline.ingestao
3. ui.py, na raiz do projeto, executável com:
     uv run python ui.py
   (spec própria no fim deste prompt; ui.py e ingestao.py não se importam)

SPEC DO pipeline/db.py (primeiro artefato)
Expõe exatamente isto, com estes nomes:
  PASTA_RAW                          Path da pasta raw/ com os sete .csv
  conectar()                         abre o ecommerce.duckdb, criando se faltar
  criar_schema(con, nome)            CREATE SCHEMA IF NOT EXISTS
  gravar(con, df, schema, tabela)    grava e devolve a contagem lida do banco

D1. CAMINHOS
    PASTA_RAW e o ecommerce.duckdb são resolvidos a partir da localização do
    próprio db.py (a pasta acima de pipeline/), nunca do diretório corrente.
    Motivo: rodar o script de outra pasta não pode criar um ecommerce.duckdb
    vazio no lugar errado, que parece ingestão quebrada.
D2. TRÊS FUNÇÕES E UMA CONSTANTE, NADA MAIS
    db.py não lê CSV, não conhece nome de tabela, não imprime nada e não
    converte tipo. Quem decide tudo isso é cada etapa.
    Motivo: as aulas 2, 3 e 4 importam este arquivo. Regra de negócio
    escondida aqui vale para todas as etapas sem aparecer em nenhuma spec.
D3. gravar
    Recria a tabela (CREATE OR REPLACE TABLE schema.tabela) com as colunas
    e os tipos do DataFrame, sem alterar nada: coluna str vira VARCHAR,
    nulo continua NULL. Não deixa view ou tabela temporária para trás.
    Devolve SELECT count(*) da tabela recém-gravada, lido do banco.
    Motivo: a contagem que aparece na tela tem que ser a do que foi
    gravado, não a do que estava na memória.
D4. CONEXÃO
    conectar() devolve a conexão aberta; quem chama é quem fecha.
    db.py não guarda conexão global.

CRITÉRIOS DE ACEITE (db.py)
- Importar pipeline.db não abre banco nem cria arquivo nenhum.
- conectar() chamado de dentro de outra pasta cria o ecommerce.duckdb na raiz
  do projeto, e não na pasta corrente.
- gravar() com um DataFrame de 3 linhas devolve 3, e rodar duas vezes
  continua devolvendo 3.

SPEC DA INGESTÃO (segundo artefato)

1. ESCOPO E NOMES
   Schema de destino: raw
   Mapa arquivo -> tabela, completo e literal:
     customers.csv   -> clientes
     order_items.csv -> itens_pedido
     orders.csv      -> pedidos
     payments.csv    -> pagamentos
     products.csv    -> produtos
     returns.csv     -> devolucoes
     shipments.csv   -> remessas
   Os nomes vão para o português porque é o vocabulário que vou digitar de
   memória num JOIN nas próximas aulas.

2. PROIBIÇÕES (a regra central desta etapa)
   Nenhuma conversão de tipo. Nenhuma linha descartada ou deduplicada.
   Nenhum nome de coluna alterado. Nenhum valor corrigido, preenchido ou
   normalizado. Data continua texto, nulo continua nulo.
   Motivo: a fronteira entre "o dado que chegou" e "o dado que eu decidi"
   precisa existir em algum lugar, e esse lugar é a passagem de raw para
   refined, na etapa 2. Se a correção acontecer aqui, a fronteira some.

3. REEXECUÇÃO
   Rodar dez vezes tem que dar o mesmo resultado que rodar uma: a tabela é
   recriada (CREATE OR REPLACE), nunca acrescentada. É o que me deixa errar
   sem medo.

4. LEITURA DO ARQUIVO
   encoding declarado como utf-8, nunca adivinhado.
   Os .csv são lidos direto da pasta raw/ (PASTA_RAW). Outras pastas do
   projeto, como csv/, são ignoradas.
   SÓ o campo vazio vira nulo. Textos como NA, N/A, NULL, None e nan
   continuam texto, exatamente como vieram no arquivo. No pandas isso é
   keep_default_na=False com na_values=[""].
   Motivo: por padrão o pandas converte esses textos em nulo mesmo com
   dtype=str. É uma correção silenciosa, exatamente o que a seção 2 proíbe,
   e uma categoria chamada "NA" viraria NULL sem aviso.
   Campo vazio não vira string vazia.

5. TIPAGEM
   Toda coluna entra como texto (dtype=str), inferência desligada.
   Motivo: inferência lê CEP ou ID com zero à esquerda como número e o zero
   desaparece sem aviso. A conversão acontece na etapa 2, onde é uma
   decisão registrada.

6. SAÍDA NA TELA
   Uma linha por tabela, com nome qualificado e contagem de linhas vinda do
   banco (não do DataFrame), milhar separado por ponto.
   Uma linha final com o total.
   Essa saída é meu único instrumento de conferência nesta etapa.
   O stdout precisa ser reconfigurado para utf-8: rodo no Prompt de Comando
   do Windows, onde acento sai embaralhado por padrão.

7. ERRO
   Antes de abrir o banco, verifique se os sete arquivos existem.
   Faltando qualquer um: liste os que faltam, diga em que pasta procurou e
   encerre com sys.exit(1). Não ingira parcialmente.
   Motivo: ingerir seis de sete tabelas em silêncio produz um dashboard
   errado que parece certo.

CRITÉRIOS DE ACEITE (ingestão)
- A execução imprime sete linhas e um total exato.
- O total é igual à soma das linhas de dados dos sete .csv (registros, sem o
  cabeçalho), contadas por outro meio que não o script, por exemplo
  SELECT count(*) FROM read_csv('raw/orders.csv') no DuckDB, arquivo por
  arquivo. Contar linhas no editor não serve: um campo com quebra de linha
  engana a contagem.
- Rodar duas vezes seguidas imprime exatamente a mesma coisa.
- SELECT * FROM raw.pedidos devolve todas as colunas como VARCHAR.
- Uma célula vazia no .csv aparece como NULL, e não como string vazia.
- Se algum .csv tiver células com o texto NA, N/A, NULL, None ou nan, o
  SELECT na tabela raw devolve esse texto, e não NULL.
- Remover um arquivo da pasta faz o script parar antes de gravar qualquer tabela.
- O script termina sozinho e devolve o terminal: nenhum processo fica de pé.

SPEC DO ui.py (terceiro artefato)
Quero explorar o banco pelo navegador, em vez de ler tabela no terminal.

U1. O QUE FAZ
    Abre o ecommerce.duckdb da raiz do projeto, instala e carrega a extensão
    `ui` do DuckDB (INSTALL ui; LOAD ui;) e chama CALL start_ui(), que sobe
    o servidor em http://localhost:4213 e abre o navegador.
U2. FICA DE PÉ ATÉ CTRL+C
    A extensão serve enquanto a conexão estiver viva. O script mantém o
    processo rodando, imprime a URL e a instrução "Ctrl+C para encerrar", e
    no Ctrl+C fecha a conexão e sai limpo, sem traceback.
    Motivo: o arquivo .duckdb aceita um único processo escrevendo. Com o
    ui.py de pé, a ingestão falha com "Could not set lock on file". Saber
    exatamente como desligar o servidor faz parte da ferramenta.
U3. NÃO CRIA BANCO
    Se ecommerce.duckdb não existir, diga que é preciso rodar a ingestão antes
    e encerre com sys.exit(1). Por isso NÃO use conectar() de pipeline/db.py,
    que cria o arquivo quando ele falta: um banco vazio aberto no navegador
    parece ingestão quebrada.
U4. SEPARAÇÃO
    ui.py não importa pipeline/ingestao.py, e a ingestão não importa ui.py:
    a ingestão não sobe servidor, não abre navegador e não depende da
    extensão ui para rodar.
U5. SAÍDA NA TELA
    Mesma regra do item 6: stdout reconfigurado para utf-8.
U6. FALHA DA EXTENSÃO
    Se INSTALL ui ou LOAD ui falhar (sem internet, extensão corrompida,
    origem diferente da já instalada, erro de DLL), o script imprime o erro
    original do DuckDB, mais uma linha dizendo que a extensão ui não
    carregou, fecha a conexão e encerra com sys.exit(1). Sem traceback.
    Motivo: o erro do DuckDB já diz a causa (por exemplo, "origem diferente"),
    e um traceback longo esconde essa mensagem no meio do ruído.

CRITÉRIOS DE ACEITE (ui.py)
- uv run python ui.py abre o navegador em localhost:4213 e o schema raw
  aparece com as sete tabelas.
- Ctrl+C devolve o terminal sem traceback, e logo depois a ingestão roda
  sem erro de lock.
- Renomear ecommerce.duckdb faz o ui.py parar com a mensagem, sem criar arquivo
  novo.
- Se a extensão ui não puder ser instalada ou carregada (por exemplo, sem
  internet e sem a extensão já baixada), o script imprime o erro do DuckDB
  numa mensagem curta e devolve o terminal com código de saída 1, sem
  traceback.

ENTREGA, nesta ordem, para cada um dos três arquivos
1. A spec como docstring no topo do arquivo, dizendo por que cada regra existe — não só o que ela manda fazer.
2. O código, com comentários apenas onde a decisão não é óbvia pelo código.
3. Uma lista final do que você assumiu e que não estava na spec. Se a lista não estiver vazia, é a minha spec que precisa melhorar.
